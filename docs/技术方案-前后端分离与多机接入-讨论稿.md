## 0. 摘要

本次变更不是「加一个页面」或「换一个数据库」，而是**部署形态与接入模型同时变化**：

1. **前后端分离**：前端从「打进 jar、由 Spring 托管」改为独立静态站点 + 纯 API 后端；
2. **多机接入**：平台从「一台机器接本地串口」升级为「中心平台纳管多个站点、多台数采主机/网关」；
3. 由此引出**是否推倒重写、是否更换技术栈**的决策。

本文给出 3 套候选方案（A 现状演进 / B Go 全栈重写 / C 边缘 Go + 中心 Spring 双栈），并给出推荐与待确认问题。
**结论未定，需先回答第 9 节的 8 个问题**。

## 1. 现状与问题

### 1.1 现状

| 维度 | 当前实现 |
|---|---|
| 后端 | Spring Boot 3.5 / JDK 21 单体（ContiNew Admin 基座 + 318 个业务 Java），模块化只完成骨架 |
| 前端 | Vue3 + TS + Arco，构建产物打进 `continew-admin.jar`，由 Spring 静态托管 |
| 存储 | MySQL 8（业务 + 历史读数组）+ Redis + SQLite 暂存 |
| 接入 | 本机串口（RTU/ASCII）、Modbus TCP、MQTT 客户端上报、数据库上报 |
| 部署 | 单机 jar + systemd/计划任务 + 自研看门狗 + Rust TUI |
| 规模 | 现场基线 100 台主机；设计目标 400 传感器 × 60 分钟压测（未执行） |

### 1.2 新需求带来的根本变化

| 变化 | 影响 |
|---|---|
| 多站点/多主机 | 需要「站点 → 网关/数采主机 → 设备 → 测点」四级模型，现有 `port → device → channel` 三级模型不够 |
| 数采主机主动上报（MQTT） | 平台从「拉」变「推」，需要 Broker、会话、离线判定、断点续传、幂等 |
| 数采主机暴露多个 Modbus TCP | 一台网关可虚拟出几十个从站，需要端点发现/批量建号/连通性探测 |
| 前后端分离 | 需要 API 域、认证、CORS、版本化、独立发布流水线 |
| 多租户/多项目（若要做产品） | 数据隔离、配额、计费、审计的要求完全不同 |

> **一句话**：现有代码是「单机采集软件」，新需求是「物联网平台」。两者的领域模型、部署模型、可靠性模型都不同。

## 2. 多机接入的三种流量（先统一语言）

```
            ┌──────────────────────────── 中心平台 ────────────────────────────┐
            │  Web 前端(独立)   REST/WS API   规则/报警   时序查询   仁科兼容输出  │
            └───────▲──────────────────▲───────────────────▲──────────────────┘
                    │ HTTPS            │ MQTT/TLS         │ JDBC
   ┌────────────────┴───────┐  ┌───────┴────────┐  ┌──────┴─────────┐
   │ 浏览器（多个站点用户）   │  │ EMQX Broker    │  │ 第三方取数系统  │
   └────────────────────────┘  └───────▲────────┘  └────────────────┘
                                       │ MQTT 上报/下发
                          ┌────────────┴─────────────┐
                          │ 数采主机 / 边缘网关（多台） │
                          │  · 本地 485/232 采集       │
                          │  · 本地缓存/断点续传        │
                          │  · 暴露 N 个 Modbus TCP    │
                          └────────────┬─────────────┘
                                       │ 485 / 网口
                                 现场传感器/仪表
```

| 流量 | 方向 | 协议 | 典型来源 |
|---|---|---|---|
| F1 网关上报 | 网关 → 平台 | MQTT 3.1.1/5.0 over TLS | 有人云、组态屏、第三方数采仪 |
| F2 平台轮询 | 平台 → 网关/设备 | Modbus TCP | 网关把多个从站映射到 TCP 端口/单元号 |
| F3 边缘代理 | 代理 → 平台 | MQTT/HTTPS | 我方部署的 Agent（仅当网关不支持 MQTT） |
| F4 北向输出 | 平台 → 第三方 | JDBC / MQTT / REST | 仁科兼容库、业主大数据平台 |

**关键判断**：F1 是主路径（网关主动上报），F2 是兼容路径（老设备只会 Modbus TCP），F3 是兜底路径（现场不允许改网关配置时）。

## 3. 目标架构（与技术栈无关）

### 3.1 分层

| 层 | 职责 | 可替换点 |
|---|---|---|
| 接入层 | MQTT Broker、Modbus TCP 轮询器、协议解码、会话与心跳 | EMQX / Mosquitto / 自研 Netty |
| 设备层 | 站点/网关/设备/测点注册、设备模板、影子状态、命令下行 | 自研 |
| 业务层 | 报警规则、报表、权限、审计、迁移转换 | 自研 |
| 数据层 | 元数据（关系库）、时序（TSDB）、缓存、对象存储 | PG/MySQL + TDengine/TimescaleDB |
| 展示层 | 独立 SPA、开放 API、WebSocket 推送 | Vue3 / React |
| 运维层 | 部署、升级、备份、监控 | Docker Compose / K8s / systemd |

### 3.2 领域模型（替代现有 port→device→channel）

```
tenant（租户，可选）
└── site（站点/项目）
    └── gateway（数采主机/边缘网关，含在线状态、固件版本、最后心跳）
        ├── device（设备，挂在网关下；也允许直连平台）
        │   └── point（测点/传感器要素：编码、单位、量程、缩放、小数位）
        └── channel（网关本地通道，可选，用于映射）
reading（测点读数，时序）
alarm_rule / alarm_record
command（下行命令：校时、继电器、重启、改配置）
```

现有 `biz_device`/`biz_sensor`/`biz_sensor_reading` 可以映射到新模型：`port` → `gateway`，`device` 保留，`sensor` → `point`。

### 3.3 MQTT 主题与报文（草案）

```
# 上行
jdrk/v1/{tenant}/{site}/{gateway}/state          # 上线/离线（LWT，retain）
jdrk/v1/{tenant}/{site}/{gateway}/telemetry      # 批量读数
jdrk/v1/{tenant}/{site}/{gateway}/event          # 报警/故障/重启
# 下行
jdrk/v1/{tenant}/{site}/{gateway}/cmd            # 平台 → 网关
jdrk/v1/{tenant}/{site}/{gateway}/cmd_reply      # 网关 → 平台
```

`telemetry` 报文（批量、带序号用于去重）：

```json
{
  "msgId": "01J...ULID",
  "gatewayId": "GW-0001",
  "ts": 1763200000000,
  "seq": 1024,
  "readings": [
    { "deviceId": "D-01", "pointCode": "temp", "value": 23.5, "quality": "good", "ts": 1763199998000 }
  ]
}
```

约定：
- QoS1 + 客户端侧持久化队列；平台按 `(gatewayId, seq)` 幂等；
- `quality`：`good / bad / stale / comm_error`；
- 时间戳统一 UTC 毫秒，网关需 NTP 或平台下发校时；
- 单条报文 ≤ 256KB，超限分片。

### 3.4 设备影子与命令

- 影子 = 最近一次上报的测点值 + 在线状态 + 配置版本；
- 下行命令带 `commandId` 与过期时间，网关 `cmd_reply` 回执；超时进死信；
- 继电器/校时等写操作必须「平台 → 网关 → 设备」全链路留痕（审计）。

### 3.5 前后端分离后的部署形态

```
                 ┌──────────────┐
   浏览器 ───────▶│ Nginx / CDN  │  静态 SPA（history 模式回退 index.html）
                 └──────┬───────┘
                        │ /api/v1/* 反向代理（同域，避免 CORS）
                 ┌──────▼───────┐
                 │ API 服务      │  JWT + RBAC + 限流
                 └──────┬───────┘
        ┌───────────────┼────────────────┐
   ┌────▼────┐    ┌─────▼─────┐    ┌─────▼─────┐
   │ MySQL/PG│    │ TDengine  │    │  EMQX     │
   └─────────┘    └───────────┘    └───────────┘
```

- 前端与 API **同域反代**为默认（无 CORS、Cookie 可用）；跨域部署时再开 CORS 白名单；
- API 统一前缀 `/api/v1`，OpenAPI 3 描述，前端用生成客户端；
- 认证：短期 Access Token（15min）+ Refresh Token；网关用 mTLS 或独立 `gatewayToken`；
- 离线部署：SPA 与镜像一起打包，不依赖公网 CDN。

## 4. 三套候选方案

### 方案 A：现状演进（Spring Boot 单体 + EMQX + TDengine，前端独立）

- 后端仍是 Spring Boot 单体，新增 `ingest` 模块接 EMQX、`tsdb` 模块写时序库；
- MySQL 保留元数据，历史读数迁 TDengine/TimescaleDB；
- 前端独立部署，Spring 不再托管静态资源；
- 复用现有权限、报表、迁移、仁科兼容代码。

**优点**：改动最小，团队零学习成本，现有 318 个 Java 与验收资产可复用；6~8 周可出可用版本。
**缺点**：JVM 常驻 1~2GB，边缘侧无法下沉；模块化仍是「单体里的包」，长期维护成本高；多租户/大规模接入需要额外改造。

### 方案 B：Go 全栈重写（边缘 Agent + 中心服务）

- 边缘 Agent：Go 单二进制，负责串口/Modbus/MQTT、缓存、断点续传、远程配置，内存 30~80MB；
- 中心：Go（Kratos/Gin/Go-Zero）模块化单体或微服务，EMQX、TDengine、PostgreSQL、Redis；
- 前端：Vue3 + TS 重写（或保留现有页面按新 API 适配）；
- 部署：Docker Compose 单机版 + K8s 集群版，交叉编译 ARM64/龙芯。

**优点**：资源效率最高，单二进制易交付、易信创适配；MQTT/长连接/高并发是 Go 的强项；运维面小。
**缺点**：业务全部重写（权限、报表、迁移、仁科兼容、审计），12~16 周起步；团队需补 Go 经验；Excel/Word 报表生态弱于 Java。

### 方案 C：双栈（边缘 Go + 中心 Spring Boot）——推荐

- 边缘 Agent 用 Go（只在需要下沉时部署；支持的网关直接用 MQTT，不装 Agent）；
- 中心保留 Spring Boot 3，新增接入模块（EMQX 消费、Modbus TCP 轮询）、时序存储、设备影子；
- 前端独立部署，继续用 Vue3；
- 现有业务代码按模块迁移，不推倒重来。

**优点**：边缘轻量 + 中心复用业务资产；风险与周期可控（10~12 周）；后续若中心也要 Go，可按模块逐步替换。
**缺点**：两套语言/两套构建；团队需要维护 Go 边缘代码；边界划分要严格（边缘不做业务）。

### 对比

| 维度 | A 演进 | B Go 重写 | C 双栈（推荐） |
|---|---|---|---|
| 代码复用 | 80% | 10~20% | 50~60% |
| 首版周期 | 6~8 周 | 12~16 周 | 10~12 周 |
| 单实例内存 | 1~2GB | 100~300MB | 中心 1~2GB + 边缘 50MB |
| 边缘部署 | 困难（JVM） | 优秀 | 优秀 |
| 多机接入 | 需新增模块 | 原生 | 原生 |
| 前后端分离 | 改造 | 原生 | 改造 |
| 信创/ARM64 | 可 | 优秀 | 优（边缘）/可（中心） |
| 团队成本 | 低 | 高 | 中 |
| 长期维护 | 中 | 低 | 中 |
| 风险 | 架构债延续 | 一次性重写风险 | 双栈复杂度 |

> 若目标是「一套可复制交付到多个业主现场的行业产品」，推荐 **C**；若是「纯公有云 SaaS、以租户和弹性为核心」，推荐 **B**。

## 5. 前后端分离实施方案（各方案通用）

| 项 | 决策点 | 建议 |
|---|---|---|
| 代码仓库 | 单仓还是双仓 | 单仓 `backend/` + `frontend/`，独立流水线；后续可拆 |
| API 契约 | 手写还是契约优先 | OpenAPI 3 契约优先，后端生成骨架、前端生成客户端 |
| 版本化 | URL 还是 Header | `/api/v1`；破坏性变更升 v2，v1 至少保留 6 个月 |
| 认证 | Session 还是 JWT | JWT（Access 15min + Refresh 7d），网关用 `X-Gateway-Token` 或 mTLS |
| 静态托管 | Nginx / CDN / 对象存储 | 现场用 Nginx（离线）；云端可 CDN |
| 跨域 | 同域反代 / CORS | 默认同域反代；跨域时白名单 + 预检缓存 |
| 前端路由 | history / hash | history + Nginx `try_files` 回退 |
| 灰度 | 前端版本与后端版本 | 后端兼容 N-1 前端；前端构建注入 `APP_VERSION` |
| 安全 | CSP / XSS / 点击劫持 | Nginx 加 CSP、`X-Frame-Options`、HSTS（有 TLS 时） |

## 6. 多机接入实施方案

### 6.1 接入模式

| 模式 | 适用 | 平台侧工作 | 网关侧要求 |
|---|---|---|---|
| M1 MQTT 直连 | 网关支持 MQTT（有人云类） | EMQX + 规则引擎/消费者 + 设备注册 | 配置 Broker、主题、Token |
| M2 Modbus TCP 轮询 | 网关只暴露 Modbus TCP | 端点管理、轮询调度、单元号映射 | 固定 IP/端口，允许平台访问 |
| M3 边缘 Agent | 网关不支持 MQTT 且不能改 | 下发 Agent 安装包与配置 | 可装二进制的 Linux/Windows 主机 |

### 6.2 注册与鉴权

1. 管理员在平台创建 `site` 与 `gateway`，生成一次性 `gatewayToken`；
2. 网关首连携带 `token + 型号 + 固件版本 + 通道清单`，平台登记并下发配置版本；
3. 之后每次连接校验 token（或 mTLS 证书），失败进审计；
4. 平台可远程禁用网关、吊销 token、下发重启/升级命令。

### 6.3 在线判定与断线续传

- LWT 主题置 `offline`；平台侧再用「最后上报时间 + 阈值」兜底；
- 网关本地环形缓存（至少 24h），断线重连后按 `seq` 续传；
- 平台按 `(gatewayId, seq)` 幂等写入，重复报文丢弃；
- 超过保留期的补传数据进入「迟到数据」分区，不阻塞实时链路。

### 6.4 时钟与配置

- 平台在 `state` 回执中下发服务器时间，网关于偏差 > 5s 时校时；
- 配置变更走「版本号 + 差量下发 + 回执」，失败回滚；
- 固件/Agent 升级走分批次灰度，失败自动回退。

### 6.5 容量设计（需业主确认）

| 指标 | 假设 | 说明 |
|---|---|---|
| 站点数 | 10~100 | 每个站点一个 `site` |
| 网关数 | 100~2000 | 每站点 1~20 台 |
| 测点数 | 1 万~10 万 | 每网关 50~500 点 |
| 采样频率 | 1s~60s | 以 5s/10s 为主 |
| 写入吞吐 | 5k~50k 点/秒 | TDengine 单节点可覆盖 |
| 历史保留 | 3 年 | 原始 90 天 + 聚合 3 年 |

### 6.6 运维面：TUI 与看门狗的替代（待后续讨论）

现有 Rust TUI + 自研看门狗是「单机时代」的产物；多机架构下运维面应优先用成熟开源组件：

| 场景 | 现方案 | 可选开源替代 | 取舍 |
|---|---|---|---|
| 进程守护 | 自研看门狗 | systemd（Linux）/ Docker restart policy / WinSW | 少一套自研代码，但失去「假死判定 + 恢复后自检」 |
| 状态面板 | Rust TUI | 1Panel / Portainer / Grafana + Prometheus | 零开发，但需额外端口与账号体系 |
| 日志 | TUI 日志视图 | journald + Loki / Grafana | 检索更强，部署更重 |
| 备份 | 内置备份 | restic / Velero | 成熟，需运维培训 |

建议：**首版保留看门狗**（已实测，负责假死重启与自检），TUI 降级为可选组件；
多站点统一运维优先接 Grafana/Prometheus，而不是自研大屏。

## 7. 数据与存储

| 数据 | 存储 | 理由 |
|---|---|---|
| 租户/站点/网关/设备/测点/模板 | PostgreSQL（推荐）或 MySQL 8 | 关系模型、事务、权限 |
| 时序读数 | TDengine（推荐）或 TimescaleDB | 高压缩、按时间分区、聚合快 |
| 实时值/会话/限流 | Redis | 低延迟 |
| 报表/导出/图片 | 本地磁盘或 MinIO | 离线可部署 |
| 仁科兼容库 | MySQL（保持 `rkmonitor` 结构） | 第三方取数不改 |

> 若坚持单库：MySQL 8 + 分区表 + 归档也能支撑 400 测点，但 2000 网关/10 万点会吃力，需提前压测。

## 9. 待决策问题（请逐项确认）

| 编号 | 问题 | 影响 |
|---|---|---|
| Q1 | 目标是「单业主私有部署」还是「多业主可复制的产品/SaaS」？ | 决定是否多租户、是否选 B |
| Q2 | 站点/网关/测点的真实规模上限（3 年）？ | 决定 TSDB 选型与容量设计 |
