# 架构决策记录（ADR）

> 状态约定：**Proposed（待确认）** / **Accepted（已采纳）** / **Superseded（被替代）**。
> 本组 ADR 是 v2（前后端分离 + 多机接入）的决策基线，确认后逐条改为 Accepted，并同步改写需求规格说明书。

## ADR-001 业务底座采用 ThingsPanel 魔改

- **状态**：**Accepted（2026-11-15 拍板 D1）**
- **背景**：需要一个能接入数千站点、设备以模板描述、可私有化/公有云部署的物联网平台。自研全栈预计 12~16 个月；调研的 10 个开源平台中，只有 ThingsPanel 原生具备「物模型 → 设备模板（含协议配置）→ 协议插件 → 插件生成器」，与「导入模板即接入」同构。
- **决策**：以 **ThingsPanel（Apache-2.0，Go + Vue3）** 为业务底座 fork 二次开发；保留版权与 NOTICE，自研多租户/RBAC、集群化、级联服务。
- **备选**：IoTSharp（.NET，免费内置多租户，但团队 .NET 成本高、无公开集群方案）。
- **排除**：ThingsBoard（BSL 1.1，免费 ≤100 设备、强制品牌）、JetLinks CE（集群/数据权限/微服务在企业版）、FastBee/OpenRemote（AGPL）、ThingLinks（禁改署名）、DeviceHive（停更）。
- **后果**：代码量小、上手快；需自行补齐多租户与集群，工作量约 6~8 人周 + 4 人周。

## ADR-002 边缘采集使用 Rust Agent

- **状态**：Proposed
- **背景**：现场存在 RS-485/232/TTL、raw TCP、RFC2217、Modbus TCP、MQTT 网关等多种形态；需要断网自治、本地缓存、远程配置、ARM64 单二进制。JVM 边缘常驻 500MB+，不可接受。
- **决策**：
  - 标准 Modbus/串口场景：优先复用现成件（mbusd、ser2net、NanoMQ、Telegraf/Fledge）；
  - 私有帧（HJ212、DL/T 645）、需要本地模板渲染与补齐补传的场景：自研 **Rust Agent**（tokio + rumqttc + serde + SQLite）。
- **后果**：边缘内存 30~80MB、可交叉编译；需维护 Rust 代码与固件升级通道。

## ADR-003 消息层使用 MQTT，分级 Broker + 自研级联服务

- **状态**：**Accepted（2026-11-15 拍板 D3：零许可路线）**
- **背景**：省级规模 3000 站 / 30 万测点，按站打包 60s 上报约 3000 msg/s；跨广域单集群不可行，必须每级独立集群 + 单向桥接。
- **决策**：
  - 设备与级联统一 MQTT 5；上下行主题分离（`d/` 上行、`c/` 下行、`cfg/` 配置、`r/` 回执）；
  - 每级一个 Broker 集群，级间单向桥接/Cluster Linking；星型直连复用同一套主题与 ACL；
  - 级联服务自研（配置下发、命令路由、补传调度、跨级鉴权、审计），约 2~3 人月。
- **Broker 选型**：**省/区域用 VerneMQ（Apache-2.0），站点用 NanoMQ（MIT）**；不使用 BSL 的 EMQX ≥5.9，也不锁定 EOL 的 5.8.x。级联用 `vmq_bridge` + 自研防环/补传服务。
- **后果**：无年费、全宽松许可；代价是失去 EMQX Cluster Linking 的“开箱级联”，级联防环与补传需自研（约 2~4 周）。

## ADR-004 时序库优先选择宽松许可方案

- **状态**：**Accepted（2026-11-15 拍板 D4：Apache IoTDB）**
- **决策**：
  - 时序主库采用 **Apache IoTDB（Apache-2.0）**：树形模型对应「站-设备-测点」，集群版开源，零许可风险；
  - 报表/BI 若强依赖 PG SQL，可用 TimescaleDB 作**旁路分析库**（不做主库）；
  - **不采用 TDengine（AGPL）**，除非后续法务明确放行；
  - 写入侧统一：批量 500~5000 行、乱序容忍、`(station, point, ts)` 幂等、按时间分区 + TTL、副本 2~3。
- **后果**：SQL 方言与 PG 不同，报表层需适配；换来零许可风险与更贴合的树形模型。

## ADR-005 前后端分离：SPA 独立部署 + OpenResty 接入

- **状态**：Accepted（方向已确认）
- **决策**：
  - 前端构建为静态资源，由 Nginx/OpenResty 托管，`history` 模式 `try_files` 回退；
  - API 统一前缀 `/api/v1`，同域反代；跨域时白名单 CORS；
  - 认证用短期 Access Token + Refresh Token；网关设备用 mTLS + 短 TTL JWT；
  - OpenResty 只做 L4 透传/SNI 分流、MQTT over WS、REST 限流与 WAF，**不终止设备 mTLS**、不做 topic 级限流。
- **后果**：前后端可独立发布与灰度；需维护 API 兼容策略（后端兼容 N-1 前端）。

## ADR-006 多租户模型（待定）

- **状态**：**Accepted（2026-11-15 拍板 D2：单租户 + 多角色 RBAC）**
- **决策**：
  - **单租户**：不做多业主租户；表结构保留 `tenant_id` 但固定为默认值，不启用租户隔离。
  - **多角色 RBAC**：管理员（由 CLI 创建，类似 HydroOJ 的超管引导方式，不开放注册）、看板员、运维员等；权限粒度 = 菜单 + 按钮 + **数据范围**（全部站点 / 指定区域 / 指定站点）。
  - 管理员账号只能通过服务端 CLI（`jdrk-cli admin create`）创建，Web 端不提供超管自助注册。
  - **权限模型单独立项讨论**（角色矩阵、数据范围继承、越权测试用例），不在本轮拍板。
- **后果**：首版权限工作量约 3 人周；后续若对外运营多业主，再启用 `tenant_id` 做隔离升级。

## ADR-007 运维面：看门狗保留，TUI 保留为可选组件

- **状态**：Proposed（D6 已明确 TUI 不裁剪，运维入口以 Web 为主）
- **决策**：多站点统一运维接 Prometheus + Grafana；单机仍保留自研看门狗（假死判定 + 自检）；Rust TUI 作为可选安装组件保留，但不再作为主运维入口。
- **后果**：减少自研面，但需补 Grafana 面板与告警规则；TUI 继续维护但优先级低于 Web。

## ADR-008 需求覆盖范围与优先级

- **状态**：**Accepted（2026-11-15 拍板 D6）**
- **决策**：
  - v2 **覆盖原 SRS 的全部需求**，不因架构升级裁剪功能；TUI、看门狗、在线同步、报表、仁科兼容输出均保留（TUI 可作为可选安装组件，但必须可用）。
  - **第一优先级：与建大仁科环境监测平台的兼容性**——`rkmonitor` 库结构输出、对象模型 → 仁科库一键转换、存量数据迁移与并行切换，先于其他新功能验收。
  - 新能力（多机接入、级联、模板）不得破坏仁科兼容链路；兼容性验收作为发布门禁。
- **后果**：范围不缩减，工期按全量需求排；仁科兼容相关 FR 必须最先打通（P0）。

## ADR-009 级联拓扑

- **状态**：**Accepted（2026-11-15 拍板 D7）**
- **决策**：**省-市-县三级逐级汇聚 + 重点站星型直连省中心**；星型站复用同一套主题与 ACL，只少一跳；不单独维护第二套协议栈。
- **后果**：区域中心需部署 Broker 集群与本地 TSDB；省中心承担直连站的接入与鉴权。

## ADR-010 交付形态

- **状态**：**Accepted（2026-11-15 拍板 D8）**
- **决策**：**私有化交付为主**：交付源码 + 多架构镜像 + 部署/迁移手册，允许 OEM 白标（替换 Logo/主题/名称），保留 ThingsPanel 等上游的 Apache-2.0 版权与 NOTICE。
- **后果**：需要维护可复现的离线镜像包与安装脚本；白标需把品牌资源做成配置而非硬编码；后续若做 SaaS，再按 D2 预留的 `tenant_id` 升级。

## ADR-011 容量与采样口径

- **状态**：**Accepted（2026-11-15 拍板 D5）**
- **决策**：
  - 设计规模 **3000 站 / 30 万测点**；默认上报周期 **60s 按站打包**；
  - 站端保留 **1s 原始值 7~30 天**，区域中心保留 1min 明细 30~90 天，省中心收 **1min 聚合 + 事件**，保留 3 年；
  - 省中心入口按 **3000~5000 msg/s、峰值 5 万点/s 写入**设计；
  - 压测以 3000 站模拟为验收基线（NFR-V2-PERF-01）。
- **后果**：存储成本可控；需要站端缓存与区域 TSDB 作为分层缓冲。

## ADR-012 开源策略与许可证合规

- **状态**：**Accepted（2026-11-15 拍板 D9）**
- **决策**：
  - 本项目为**完全开源项目**，代码仓库公开；采用 **Apache-2.0**（与 ThingsPanel 及主流依赖兼容）。
  - **许可证红线**：核心链路不引入 AGPL（TDengine、iotagent-json）、BSL（EMQX ≥5.9、ThingsBoard 4.4+）、SSPL/Elastic 等传染性或限制性许可；边缘/工具链中的 GPL（ser2net/socat）仅在独立进程、非链接分发时使用，并在 NOTICE 中说明。
  - 交付物包含 `LICENSE`、`NOTICE`、第三方依赖清单与 SBOM；OEM 白标必须保留上游版权声明。
  - 依赖升级前做许可证扫描（CI 门禁），新增依赖需在 PR 中说明许可证。
- **后果**：全部自研代码可公开复用；商业/OEM 通过服务与实施而非闭源授权获利。

## ADR-013 启动方式：先 2 周 PoC

- **状态**：**Accepted（2026-11-15 拍板 D10）**
- **决策**：全面开工前先做 **2 周 PoC**，范围：
  1. 测试机部署 ThingsPanel + IoTDB + VerneMQ/NanoMQ；
  2. 跑通「模板导入 → Modbus 模拟器采集 → MQTT → IoTDB → 看板」最小链路；
  3. 1000 站模拟压测（60s 打包上报），记录写入/查询/资源基线；
  4. 验证多租户改造成本、白标点、级联桥接与断网续传。
- **出口条件**：模板 5 分钟内出数；1000 站 1 小时无 5xx；IoTDB 写入与查询达标；产出 PoC 报告并校准工期。
- **后果**：PoC 不通过则回到 D1 重新评估底座；通过则按 P1 全面开工。
