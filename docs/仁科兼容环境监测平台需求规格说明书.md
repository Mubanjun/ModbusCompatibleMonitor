## 1 引言

### 1.1 编写目的

明确「仁科兼容环境监测平台」的建设目标、功能范围、质量指标与验收标准，统一产品、开发、测试与运维的认知，降低因协议与需求理解偏差导致的返工风险。本文档是后续《概要设计说明书》《数据库设计说明书》《接口设计说明书》与《测试用例》的输入。

### 1.2 项目背景

山东建大仁科（以下简称「仁科」）的环境监测平台功能完善、设备生态成熟，但其设备侧私有通讯协议未公开，无法在本项目中直接复用。同时，现场已大量部署仁科的监控主机与 485 传感器，替换成本极高。

本项目采用差异化策略：**只使用仁科已公开发布的 ModBus 从站规约与标准 Modbus 协议**（即《小主机 ModBus 从站接口通信详解（标准 ModBus 规约）》《小主机 ModBus 从站接口通信详解（RS-ModBus 规约）》《RS-RJ-K 二次开发接口 V2.4》《RS-QXZ-M 智能监控主机使用说明书》《RK.NetDevice.SDK》等），开发一套功能与仁科平台相仿的环境监测平台，具备以下能力：

1. 通过监控主机的 485 接口（或直接连接仁科 Modbus 传感器）完成数据采集；
2. 提供实时监控、设备管理、继电器控制、告警、历史数据查询等业务功能；
3. 将数据上报至与仁科兼容的数据库，并支持 MQTT 等外部系统对接；
4. 提供终端管理端（TUI）与自研独立守护进程，保障系统稳定与自恢复；
5. 最终实现**无损替换现有仁科软件环境**。

**明确不做的事**：不反编译、不破解、不依赖仁科未公开的私有协议或私有库；所有通讯实现必须可追溯到公开规约或标准 Modbus 规范。

| 术语 | 说明 |

| 从站 / Slave | Modbus 通讯中的被控设备，本项目中指监控主机或 485 传感器 |

| 模拟量 | 通道上的测量值，每通道含模拟量 1（如温度）与模拟量 2（如湿度） |
| 节点 / Node | 数据模型中的最小采集单元，等价于「设备 + 通道 + 模拟量」的组合 |
| 继电器 / Relay | 主机可控制的开关输出，标准规约下为 8 路 |
| 485 | RS-485 串行总线，Modbus RTU 的主要物理层 |

| RS-Modbus | 仁科自有 Modbus 从站规约，寄存器映射与标准规约不同 |
| 信令 | 采集过程中收发的原始报文（TX/RX 十六进制帧及解析结果） |
| IPC | 进程间通信（Inter-Process Communication） |
| TUI | 终端用户界面（Terminal User Interface），在本地控制台或 SSH 下运行的字符界面客户端 |
| 看门狗 / Watchdog | 独立进程，负责监控主进程存活并触发自恢复（本项目为自研，非系统守护） |
| 进程管理 | 看门狗负责后端守护与自恢复，systemd（Linux）/ WinSW 或计划任务（Windows）负责引导与开机自启；**不引入 pm2 等外部进程管理器** |
| ContiNew Admin | 现代开源多租户中后台管理框架（Spring Boot 3.5 / Vue3 + Arco Design），本项目以它为基座，并已把其 Maven 工程改造为 Gradle |
| 暂存 / 缓冲 | 数据在本地 SQLite 落盘，按策略批量上报的中间层 |
| 设备分组 / 分组树 | V1.2 起引入的**层级式设备组织单元**，语义等同操作系统的文件夹：有父子层级、可重命名/移动/排序，一台设备只归属一个分组 |

| 未分组 | 系统的默认根分组（不可删除、不可改名）；未显式归组的设备都落在这里，保证「任何设备都有分组」 |

| 一键转换（转换脚本） | 把对象化存储转换并写入仁科脚本要求的表结构（tbhistory 等）的工具/接口；兼容性靠「转换产物一致」保证（FR-MIG-08） |
| 授权分组 | 角色在数据权限中被授予可见的分组集合；可见范围 = 授权分组及其子树（FR-DEV-20） |
| SRS | 软件需求规格说明书 |

## 2 项目概述

### 2.1 产品定位

一套「仁科兼容」的环境监测平台软件，以 **C/S 架构**交付：

- **客户端（管理端）**：TUI 终端程序（Rust + ratatui，字符界面），负责系统状态呈现、依赖检查与修复、服务启停、备份恢复、离线改密等运维操作；不承担后端进程守护职责；
- **服务端**：Spring Boot 后端服务，负责协议采集、数据处理、存储、上报与 Web API；
- **Web 端**：浏览器看板（基于 ContiNew 前端，Vue3 + TypeScript + Arco Design），面向日常业务用户。

产品在功能上对齐仁科平台（实时监控、设备管理、报警、历史数据、数据库接入），在实现上完全独立，并可在现场**无损替换**仁科原软件。

### 2.2 建设目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 兼容采集：支持标准 Modbus RTU、RS-Modbus、Modbus TCP 等协议，接入仁科监控主机与 485 传感器 | 现场至少 3 类设备完成连通采集 |
| G2 | 功能对齐：实时看板、设备增删、继电器控制、报表查询、报警可用 | 与仁科平台功能对照表逐项通过 |
| G3 | 数据上报：支持 MQTT 与 6 类以上数据库上报，含一键同步 | 目标库数据与源数据一致，支持新旧判定 |
| G4 | 稳态运行：独立看门狗与自恢复，长期无人值守 | 连续运行 30 天无人工干预 |
| G5 | 无损替换：可替换仁科原软件并保留原数据结构与使用习惯 | 在真实/演练环境完成切换并回退演练 |
| G6 | 易维护：模块对象化、命名规范统一，便于低上下文成本的增量维护 | 单文件规模、命名规范、依赖方向通过检查 |

### 2.3 业务流水线与启动时序

整体业务流水线（启动链路）定义如下，作为看门狗、后端与客户端协同的强制时序：

| 阶段 | 名称 | 执行方 | 关键动作 | 失败处理 |
|---|---|---|---|---|
| S0 | 启动守护进程 | 看门狗 | 系统引导时由 systemd（Linux）/ WinSW 或计划任务（Windows）自动拉起看门狗（FR-SYS-07），或人工执行 start-monitor；看门狗获取单实例锁 | 已存在实例则退出并记录 |
| S1 | 依赖检查与初始化 | 看门狗 | 检查 JDK/运行时、业务库与 Redis 连通性、端口、目录权限、磁盘余量，输出日志 | 检查失败则记录并可重试，不阻塞后续阶段 |
| S2 | 拉起后端 | 看门狗 | 以受管子进程方式启动 Spring Boot 服务，等待健康检查通过或首次心跳 | 超时/失败重试，达重启限流阈值则停机告警 |
| S3 | 启动终端管理端（可选） | TUI 客户端 | 运维人员本地控制台或 SSH 启动 TUI，展示状态并执行运维操作 | 启动失败不影响平台运行（平台可无界面常驻） |
| S4 | 打开浏览器看板 | TUI 客户端 / 用户 | TUI 调用默认浏览器打开看板地址并携带一次性票据，或回显地址 | 打开失败则回显地址并提示 |
| S5 | 点击登录配置系统 | 用户 / Web | 登录后进入配置向导（设备、串口、上报） | 配置校验不通过则阻断并提示 |

### 2.4 用户角色

| 角色 | 使用界面 | 主要职责 | 权限要点 |
|---|---|---|---|
| 业务用户 | Web 看板 | 查看实时/历史数据、导出、处理报警 | 只读为主，按角色授权 |
| 运维/配置人员 | Web 看板 | 设备增删改、参数配置、继电器操作、上报配置 | 设备与配置写权限 |
| 系统管理员 | TUI 管理端 + Web | 启停服务、修复依赖、备份恢复、离线重置超管密码 | 系统级权限，需操作系统管理员提权 |
| 系统进程 | 无界面 | 看门狗、采集调度、上报任务 | 仅本地 IPC，不对外暴露 |

### 2.5 运行环境

| 项 | 要求 |
|---|---|
| 服务端操作系统 | Windows 10/11 x64；主流 Linux（Ubuntu 22.04+/CentOS 7+/麒麟/统信）x86_64，可选 ARM64 |
| 客户端操作系统 | 与服务器同机部署（默认）或独立部署；以本地控制台或 SSH 终端运行，支持 UTF-8 与 256 色，Windows/Linux 均可，**无需图形桌面环境** |
| 运行时 | JDK 21（随包分发精简 JRE/jlink 运行时）；TUI 客户端为单二进制、无额外运行时依赖，建议在 tmux/screen 内运行以支持会话驻留 |
| Web 浏览器 | Chrome/Edge 100+、Firefox 100+ |
| 硬件建议 | 4 核 CPU、8GB 内存、128GB 可用磁盘；串口或串口服务器 |
| 网络 | 局域网；MQTT/数据库目标可达 |

### 2.6 设计原则

1. **协议合法**：仅实现公开规约与标准 Modbus，不触碰私有协议。
2. **对象自治**：每个业务能力是一个独立对象/模块，边界清晰、依赖单向，便于局部替换与低成本维护（对应「避免过度消耗 Token 与人力」）。
3. **接口优先**：模块间通过稳定契约交互，内部实现可替换。
4. **默认安全**：最小权限、离线可运维、关键操作可审计。
5. **可观测**：日志、信令、指标三者可用，问题可定位。
6. **渐进兼容**：先读后写、先监控后控制、先在演练环境替换。

## 3 总体架构

### 3.1 逻辑架构

系统自上而下分为四层：

| 层次 | 组件 | 职责 |
|---|---|---|
| 表现层 | TUI 终端管理端、浏览器看板 | 状态呈现、运维操作、业务操作 |
| 服务层 | Spring Boot 应用（ContiNew Admin 基座 + 业务模块） | REST API、权限、业务编排 |
| 业务能力层 | 设备管理、协议适配、采集调度、暂存、上报、同步、告警、信令 | 领域能力，独立对象实现 |
| 资源层 | 串口/网口、SQLite、业务库、上报目标库、MQTT Broker | 数据与通道 |

### 3.2 进程模型与 IPC

| 进程 | 数量 | 职责 | 生命周期 |
|---|---|---|---|
| TUI 客户端进程（可选） | 0..1 | 终端状态显示、依赖检查、启停控制、备份恢复、离线改密 | 运维会话内按需启动，退出不影响平台 |
| 后端 Java 进程 | 1 | 采集、业务、Web API | 由看门狗拉起，受看门狗保护 |
| 看门狗进程 | 1 | 监控后端存活、按策略重启、执行恢复后自检 | 随系统启动，独立于后端，不使用 pm2 等外部进程管理器 |
| 采集工作进程（可选） | 0..N | 串口密集场景下隔离采集负载 | 由后端按需拉起 |

**IPC 约定**

| 通道 | 用途 | 协议 | 说明 |
|---|---|---|---|
| IPC-1 | TUI ↔ 看门狗/后端 控制面 | 本地回环 HTTP + 一次性令牌 | 启停、状态、健康检查、日志查询 |
| IPC-2 | 后端 ↔ 看门狗 | 心跳文件 + 本地套接字/命名管道 | 心跳、重启指令、崩溃上报 |
| IPC-3 | 后端 ↔ 采集工作进程 | 本地套接字 + 长度前缀消息 | 仅在拆分采集进程时启用 |

要求：IPC 仅监听本地回环或本地套接字，不对外暴露；所有控制面请求需鉴权；IPC 失败不得导致业务数据丢失。

进程管理职责单一：后端与看门狗的启动/重启一律由**看门狗**负责，TUI 只下发控制指令并展示状态，禁止出现两套进程管理逻辑。

### 3.4 部署与目录结构（建议）

~~~
<安装根目录>/
  app/            后端可执行与依赖
  client/         TUI 终端客户端（单二进制）
  runtime/        精简 JRE
  config/         配置文件（含数据源、采集、上报）
  data/           SQLite 暂存、缓存、导出
  logs/           运行日志与审计日志
  backup/         备份包
  tools/          看门狗、备份恢复、诊断脚本
~~~

要求：数据与程序分离，卸载/升级不丢失 data 与 config；目录可配置；路径不含中文与空格为默认约束（需兼容含中文路径，见 NFR-COMPAT）。

### 3.5 核心数据流

~~~
传感器/主机 --485/TCP--> 协议适配器 --> 采集调度器 --> 数据总线
                                                   |--> 实时缓存(内存) --> Web 看板
                                                   |--> SQLite 暂存 --> 上报任务 --> MQTT / 目标数据库
                                                   |--> 报警引擎 --> 报警记录/通知
                                                   |--> 信令日志 --> 信令监视界面
~~~

设计要点：采集与上报解耦；实时看板读内存缓存，历史查询读目标库/暂存库；任一环节不可用不得阻塞其他环节（背压与降级）。

### 3.6 业务模块化与可插拔（V1.4 新增）

平台采用「壳 + 业务模块」：M0 壳只提供登录/用户/角色/菜单/部门/字典/系统配置/文件/通知/日志/在线用户/数据权限/仪表盘容器；M1~M8 为自包含业务模块。

- 四条铁律：壳不依赖业务；模块自包含；模块间零直接依赖；壳能力必须复用。
- L1 构建期插件：Gradle 子模块 + jdrk.modules.<id>.enabled 开关，交付一个 jar，保留升级 L2 契约。
- 每个模块必备 manifest、独立 DDL、菜单/权限种子、前端入口、README；前端用显式 registry，禁用模块不得进首屏 chunk。

| 模块 | 名称 |
|---|---|
| M1 | 设备管理（含分组/位置/地图） |
| M2 | 采集与监视 |
| M3 | 报警 |
| M4 | 数据上报（含一键转换） |
| M5 | 数据同步 |
| M6 | 查询与分析（含分析板） |
| M7 | 运维与诊断 |
| M8 | 预测（仅契约/SPI/Noop） |

### 4.3.1 分组树设计约定（V1.2 新增，配套 FR-DEV-14~21）

> 本节回答「类似文件夹管理」的具体口径，避免开发与验收各自理解。凡是本节未明确的，
> 一律以「与操作系统文件夹行为一致」为准。

**（1）为什么是树、为什么是单父**

现状 `biz_device.group_name` 是一个自由文本字段（`varchar(50)`，前端就是一个输入框），
只能做等值筛选，无法表达「厂区 → 车间 → 工段 → 点位」这类现场真实结构，也无法做组级统计与
组级批量操作。设备规模上来后（见 NFR-SCALE-05），靠文本约定命名必然失控。

因此升级为分组树。**一台设备只归属一个分组**（单父），理由：
① 与文件夹语义一致，用户不需要理解「多标签」概念；② 归组关系唯一，统计口径唯一，
不会出现「同一台设备在两个组里被重复计数」；③ 移动语义清晰（从 A 组移到 B 组）。
若现场确有「一台设备多个视角」的需求，用 FR-WEB-04 的多视图（按分组/端口/区域）解决，
不引入多对多归属。

**（2）层级与命名**

| 规则 | 约定 |
|---|---|
| 最大层级 | 默认 5 层，可配置 1~8；超过即拒绝并提示「层级超过上限（N 层）」 |
| 同级重名 | 同一父分组下名称唯一（大小写不敏感，去首尾空格后比较）；不同父分组下可重名 |
| 名称长度 | 1~50 字符；禁止 `/`、`\`、`..` 与不可见控制字符（分组路径用 `/` 拼接，避免歧义） |
| 排序 | 同父内按 `sort_no` 升序，支持拖拽/上移/下移；新分组默认排在末尾 |
| 根分组 | 内置「未分组」为树根，`parent_id = 0`，不可删除、不可改名、不可移动；新建的顶层分组与其同级 |
| 空分组 | 允许存在（现场常先建结构后接设备），树节点显示 `0` |

**（3）删除规则（必须二选一，不允许“随手删”）**

| 场景 | 行为 |
|---|---|
| 空分组（无设备、无子分组） | 直接删除（逻辑删除），记审计 |
| 仅有设备 | 阻止，提示「该分组下还有 N 台设备」，提供「全部移入未分组后再删除」按钮（二次确认） |
| 仅有子分组 | 阻止，提示「该分组下还有 N 个子分组」 |
| 设备与子分组都有 | 阻止，同上；提供「递归移入未分组后再删除」（二次确认，展示将被移动的数量） |

任何情况下删除后都必须保证 `biz_device.group_id` 指向存在的分组（由服务端在同一事务内保证，
并提供升级后的巡检接口 `GET /env/device/group/orphans` 查孤立引用）。

**（4）移动与防环**

- 移动分组 = 改 `parent_id`：目标不能是自己、也不能是自己的子孙（服务端校验，前端拖拽同样提示）；
- 移动后子树路径（`path`）需级联更新，且移动后子树深度不得突破层级上限；
- 批量移动设备：一次事务内完成，返回成功/失败明细；
- 所有移动写操作日志（谁、何时、从哪个分组、到哪个分组、影响多少设备）。

**（5）统计口径（前端树节点徽标）**

| 指标 | 口径 |
|---|---|
| 本组设备数 | `group_id = 当前分组` 的设备数（含停用） |
| 含子分组设备数 | 当前分组子树内（含自身）设备数 |
| 在线数 / 异常数 | 分别按「在线」与「通讯异常/报警」设备状态统计，口径与 FR-WEB-03 一致 |
| 停用设备 | 计入设备数，但不计入在线数；树上可用「仅看启用」开关排除 |

统计必须由服务端聚合返回（不允许前端拉全量设备自行统计），否则 2000 台以上设备会拖死列表页。

**（6）与端口的关系（正交，不替代）**

分组是**逻辑组织维度**，端口是**物理接入维度**，两者正交：一台设备同时属于「某端口」与
「某分组」。因此：

- 不允许用分组替代端口来做采集调度（同一分组内的设备可能分布在多个端口、多个波特率上）；
- 端口删除/停用时，其下设备的分组归属不变；
- 分组不参与轮询顺序计算（轮询顺序仍按 FR-ACQ-04 的端口内顺序）；分组只影响查看与批量维护。
- 若现场希望「按分组设采集间隔/优先级」，走 FR-ACQ-12（P2），不改变上述正交关系。

**（7）性能与并发**

- 树接口一次返回整棵树（含计数），2000 台设备 / 500 个分组下 ≤ 1s；
- 设备列表按分组过滤走 `group_id` 索引；「含子分组」走 `path` 前缀匹配，禁止逐层递归查库；
- 两个用户同时移动同一分组时，后提交者收到「分组已被他人移动」提示，而不是静默覆盖。

**（8）存量迁移**

升级脚本按 §6.2 的 `biz_device_group` 执行：把 `group_name` 去重后建为「未分组」下的一级分组，
设备指向对应分组；`group_name` 为空/NULL 的设备归入「未分组」。迁移后 `group_name` 只读保留
（导出与第三方对接仍可用），前端不再写入。

**（9）分组数据权限的落地方式（V1.3，业主确认要做，优先集成而非自研）**

目标：设备树内「能看到 / 能操作」的范围按授权分组控制，粒度到子树（`厂区A/进水口` 及其子分组）。

**选型结论：复用底座已有的数据权限模块，不自研权限内核。**

已核实的既有能力（本项目同版本 BOM 内已存在，2.16.0）：

| 构件 | 提供什么 | 说明 |
|---|---|---|
| `continew-starter-extension-datapermission-core` | `@DataPermission` 注解（`tableAlias`/`id`/`deptId`/`userId`/`roleId` 等）与 `DataScope` 枚举 | `DataScope` 取值 **ALL / DEPT_AND_CHILD / DEPT / SELF / CUSTOM**，即业界常见的「全部 / 本部门及以下 / 本部门 / 仅本人 / 自定义」5 档 |
| `continew-starter-extension-datapermission-mp` | `DefaultDataPermissionHandler implements com.baomidou.mybatisplus.extension.plugins.handler.DataPermissionHandler` | 即 **MyBatis-Plus 官方数据权限插件**（3.5.17 已在本项目依赖内），在 SQL 层自动追加 `WHERE` 片段 |
| 前端 Arco Design `Tree` | `checkable` + `v-model:checked-keys` + 半选态 | 角色授权界面直接用，无需引入新的树组件 |

因此**不需要**引入 Casbin / OPA / 自研鉴权框架：
行级过滤的落点本来就是 SQL，MyBatis-Plus 插件是这条链路上最省的一层，而 ContiNew 已经把「注解 + 拦截器装配 + 角色数据范围解析」做好了。

**只需要自研的一层（约一个 handler）**：底座默认处理器按**部门**（`sys_dept`）拼条件，而本平台要按**设备分组**。做法：

1. 引入上述两个构件（同 BOM 版本，**不新增任何第三方依赖**）；
2. 角色新增「设备数据范围」字段，取值复用 `DataScope`：`ALL` / `GROUP_AND_CHILD` / `GROUP` / `SELF` / `CUSTOM`；`CUSTOM` 关联「角色-授权分组」关系表；
3. 自研 `DeviceGroupDataPermissionHandler implements DataPermissionHandler`：只对涉及 `biz_device` / `biz_sensor` / `biz_sensor_reading` 的查询生效，把授权分组解析为
   `group_id IN (授权分组及其子树 id)`（子树用 `path` 前缀一次查全，不递归），不相关 SQL 原样返回；
4. 授权集合按 `userId + 角色版本` 缓存，角色/分组变更时主动失效（验收要求「≤1 分钟生效」）；
5. 越权防护不只靠 SQL：单条 `GET/PUT/DELETE` 在服务层再做一次 `assertVisible(group_id)`，避免「知道了 id 就能查」；
6. 导出、报表、看板、报警记录等**所有**按设备取数的接口必须走同一套过滤（用测试逐接口覆盖，不接受「列表做了、导出忘了」）。

> 备注：`SELF`（仅本人创建）在本平台意义有限（设备通常由管理员统一建档），保留枚举但首版可只在设备表生效。
> 若后续要做「按区域/按厂区」的第二维度，扩展点仍是同一个 handler，不需要推翻。

| FR-MIG-09 | 转换结果校验 | 转换前后按「表 + 时间窗 + 抽样」比对行数与关键字段（设备名/地址/节点/时间/值），输出可查报告；不一致项可定位到具体传感器与时间点 | P1 | 校验报告含行数对比、抽样明细、不一致清单；人为改一条后能被检出 |

### 4.19 预测接口预留（FR-PRED）

| 编号 | 需求名称 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR-PRED-01 | 预测契约 + SPI + Noop | 本轮不写预测算法；固定预测提供者契约（输入：传感器/时间窗；输出：预测值/置信度/模型版本/生成时间），提供 PredictionProvider SPI 与 Noop 实现；通过 jdrk.modules.predict.enabled 或系统配置控制；未启用/无提供者时返回明确「未启用」语义，不得 500 或刷异常日志。 | P1 | 契约与 SPI 可编译；Noop 返回未启用；关闭模块无异常日志；页面/接口无 500。 |

| 变更 | 说明 |

**biz_sensor（传感器对象，一等公民）**

| 字段 | 类型（MySQL） | 说明 |

| 字段 | 类型（MySQL） | 说明 |
|---|---|---|
| id | bigint 主键 | 读数行 |
| sensor_id | bigint NOT NULL | 传感器对象 ID |
| record_time | datetime NOT NULL | 记录时间 |
| raw_value | decimal(18,4) | 原始寄存器值 |
| value | decimal(18,4) | 工程量（按系数/偏移换算） |

**与现有模型及仁科表的映射**

| 现模型（V1.2 及以前） | 对象模型（V1.3） | 仁科目标表（转换产物） |
|---|---|---|
| `biz_device` + `biz_channel` 的「设备+通道+模拟量」组合 | 一条 `biz_sensor` | `tbhistory.DeviceName` / `DeviceAddr` / `NodeId` |
| `biz_data`（宽行，固定 Hum/Tem 等列） | 多条 `biz_sensor_reading`（每传感器每时刻一行） | `tbhistory` 的一行（按 DeviceAddr+NodeId+RecordTime 聚合成宽行） |
| `biz_alarm_record` | 保留（关联 `sensor_id`） | `tbalarm` |

> 设计取舍：观测值用**窄表**而不是「一类传感器一张表」，理由是现场要素会随模板增加（电导率/浊度/氨氮/ORP/余氯/离子…），
> 动态建表会让迁移、备份与同步全部复杂化；窄表 + 要素字典 + `ext_json` 能覆盖「新传感器不改表结构」的目标，
> 且 `(sensor_id, record_time)` 唯一键天然满足 FR-MIG-08 的幂等要求。
> 宽表只出现在转换产物侧，由脚本按仁科脚本要求聚合生成。

### 6.3 上报目标库模型（DR-03，仁科兼容 —— 转换目标）

> **V1.3 语义调整**：本节描述的 `rkmonitor` 表结构**不再是本平台的内部存储**，而是
> 「一键转换脚本」（FR-MIG-08）与同步引擎（FR-SYNC）的**输出目标**。内部存储见 §6.2.2 的对象化模型。
> 调整原因：业主要求以易用为主，每支传感器及其数据作为独立对象入库，不为了兼容而扭曲内部结构；
> 兼容性通过「产物一致」而不是「内部一致」来保证。
>
> 因此本节的地位是：**契约**——转换脚本/同步写出的东西必须与仁科脚本建出的库逐表逐字段一致，
> 这样第三方取数程序与「无损替换」才不用改造。内部表可以按本平台需要自由演进。

### 6.6 主键与一致性（DR-06）

- 历史数据 ID 采用全局唯一方案（如 UUID 去横线 32 位或雪花 ID），与仁科 varchar 主键兼容；建议与仁科保持同构以便幂等 upsert。
- 幂等键：设备地址 + 节点 + 采集时间戳 + 模拟量序号，用于去重。
- 时间水位线：以 (RecordTime, ID) 组合作为增量同步游标。
- 事务边界：单批上报事务化，失败整批回滚后重试，避免半批写入。

## 附录 A：标准 ModBus 规约寄存器映射摘要（依据 R1）

通讯参数：8 位数据位、无校验、1 位停止位、CRC16、波特率 4800bit/s；采用 Modbus RTU；16 位数据高字节在前。

| 685 | 时间-月 | 16 位无符号，1 至 12 | 读/写 |

## 附录 B：RS-Modbus 规约说明（依据 R2）

- 适用范围与硬件同附录 A；主机按键将「ModBus 从规约」设为 RS-Modbus 规约。
- 寄存器地址：0000 为模拟量 2 原始值（16 位无符号整型），0001 为模拟量 1 原始值（16 位有符号整型）。
- 仅使用功能码 0x03。
- 从站地址对应主机 32 个通道中的第 1 个通道；多台主机同时通讯时，从站地址按 1、33、65、97、32N+1 规划。
- 解析约定：温度低于 0 摄氏度以补码上传，例如 FF9B 十六进制等于 -101，即 -10.1 摄氏度；湿度 0292 十六进制等于 658，即 65.8%RH。
- 报文示例（从地址 0x02，读通道 1 的模拟量 1/2）：问询 02 03 00 00 00 02 C4 38；应答 02 03 04 02 92 FF 9B 69 3D。
