# 串口阻塞 / 端口无法释放 —— 根因分析与修复说明

| 项目 | 内容 |
| --- | --- |
| 现象 | 后端进程无法终止（Stop-Process / taskkill 均报 Access denied），exe 被锁、COM3 被占；禁用再启用设备也只是暂时缓解 |
| 定位时间 | 2026-09-20 |
| 结论 | 不是环境问题，是后端**串口连接策略**与**IPC 设计**的两个真实缺陷 |
| 状态 | 已修复并编译通过（cargo check 0 error，新二进制实测可 12 ms 干净退出） |

---

## 1. 复现与证据

- 真机联调时后端对 COM3 采集正常（20/20，RTT 40~60 ms）；为加入 RTT 修复需要重启后端。
- Stop-Process -Force / taskkill /F 均报 **Access denied**；
- OpenProcess(PROCESS_TERMINATE) 成功，但 TerminateProcess 返回 **ERROR_ACCESS_DENIED(5)**；
- Get-Process -Id 报「找不到进程」，但 Get-Process jdrk-monitor 仍能列出，netstat 显示该 PID 仍 LISTENING；
- Sysinternals handle64 扫描 COM3 与 exe 均无匹配句柄；
- 最终状态：进程停在「正在终止但被挂起的内核 I/O 卡住」，exe 与串口都无法释放。

---

## 2. 根因一：传输层用了「同步、不可取消」的串口读写

serialport-4.10.1/src/windows/com.rs：

- 第 64~73 行 CreateFileW(..., FILE_ATTRIBUTE_NORMAL, 0) —— **没有 FILE_FLAG_OVERLAPPED**；
- 第 210 行 fn read() 直接调用**同步** ReadFile(..., null_mut())。

同步 IRP 一旦被 USB 串口驱动挂起（设备复位 / 掉线 / 驱动异常），没有任何 API 能取消它：

- CancelIoEx 只对异步（overlapped）I/O 有效，对同步 I/O 无效；
- TerminateProcess 会一直等待该 IRP 完成，进程因此卡在终止态；
- 进程不退出，exe 的映像句柄与 COM3 的句柄都不会释放。

这就是「后端不能处理串口阻塞、端口不能释放」的物理层原因。

---

## 3. 根因二：应用层 IPC 策略缺失

| 缺陷 | 后果 |
| --- | --- |
| LinkHandle 每个请求 await oneshot，**没有 tokio::time::timeout** | worker 一旦卡住，采集任务永久挂起，前端既拿不到新数据也看不到报错 |
| 配置里的 round_timeout_ms **从未被使用** | 「整轮软超时」名存实亡 |
| 链路失败后 ensure_open() 只在 link.is_none() 时重开 | **连续失败不会关闭重连**，FR-10（串口掉线自动重连）实际未实现 |
| 没有 Shutdown / Cancel 机制 | worker 线程无法退出，串口永不主动关闭，进程退出只能靠强杀（而强杀又会卡住） |

---

## 4. 修复内容

### 4.1 传输层：改为可取消的重叠 I/O（Windows）

新增 backend/src/modbus/serial.rs（跨平台抽象）与 serial/win.rs：

- CreateFileW(..., FILE_FLAG_OVERLAPPED)；
- 读 / 写都用 OVERLAPPED + WaitForSingleObject(event, timeout)，**超时即 CancelIoEx 并回收**；
- 暴露 Canceller（内部为 Arc 句柄，Send + Sync）：**任意线程调用 cancel() 即可打断该句柄上挂起的 I/O**；
- Drop 时先 CancelIoEx 再 CloseHandle，保证端口一定释放；
- COMMTIMEOUTS 设为「立即返回已有数据」，超时完全由我们控制，不再依赖驱动的超时行为。

Linux：serial/posix.rs 继续用 serialport（POSIX VTIME 读有界），Canceller 为空实现。

### 4.2 IPC 层：请求超时 + 强制取消

LinkHandle::request()：

- 每个请求都套 tokio::time::timeout(ipc_timeout)；
- ipc_timeout = response_timeout_ms * (retries+1) + retry_interval_ms * retries + 2000 ms；
- **超时后立即 CancelIoEx**，返回质量位 timeout 的错误，采集循环不再被拖死。

### 4.3 连接策略：连续失败自动关闭重连

- Worker 记录 consecutive_failures，成功即清零；
- **连续失败 >= 5 次，关闭串口并重开**（真正实现 FR-10）；
- reopen() 统一处理 wired / lora / simulator 三种链路。

### 4.4 停机：优雅退出

- 新增 LinkRequest::Shutdown；LinkHandle::shutdown() 让 worker 关闭串口并结束线程；
- app.rs 注册 tokio::signal::ctrl_c()：收到信号 -> link.shutdown() -> exit(0)；
- 即使底层仍有异常，重叠 I/O 可被取消，不再出现「杀不掉的进程」。

### 4.5 整轮软超时（补齐 round_timeout_ms）

- poll_round(..., deadline: Option<Instant>)；RS-Modbus 逐通道、Std-Modbus 分片读取前都检查 deadline；
- 到点后剩余通道写入质量位 timeout，整轮按时收尾。

### 4.6 采样携带真实 RTT

- 采集层从链路状态读取 last_rtt_ms 写入每条采样；前端卡片不再显示 0 ms（模拟器实测 avg_rtt_ms=4）。

---

### 4.7 根治：读前先查输入队列（关键）

debug 日志暴露了更深的根因：

    DEBUG read pending -> cancelled cancel=1 completed=0 got=0   (反复出现)

- serialport 原始配方把 ReadTotalTimeoutMultiplier 设为 MAXDWORD，
  而 Windows 总超时 = Multiplier * 请求字节数 + Constant，**等于无限**；
  因此每次读都会在驱动里留下**挂起的内核 IRP**；
- 强杀时正好命中挂起 IRP，驱动不完成取消，进程卡在终止态、端口被驱动锁住。

最终修复（serial/win.rs::read_timeout）：

1. 先用 ClearCommError 读取 COMSTAT.cbInQue；
2. **只有 cbInQue > 0（确实有数据）才发 ReadFile**，并按可用字节数收帧；
3. 这样 ReadFile 立即完成，**根本不产生挂起 IRP**；
4. 超时配方改为 pyserial 同款：ReadIntervalTimeout=MAXDWORD / Multiplier=0 / Constant=20，
   并检查 SetCommTimeouts 返回值。

### 4.8 控制台控制处理器

注册 SetConsoleCtrlHandler，处理 CTRL_C / CTRL_BREAK / CTRL_CLOSE（关窗）/
CTRL_LOGOFF / CTRL_SHUTDOWN：先 CancelIoEx + CloseHandle 释放串口再退出，
避免通过关窗、注销、关机时留下占用。

### 4.9 优雅停机接口与脚本

- 后端新增 POST /api/shutdown：关闭串口后退出；
- 新增 tools/stop-backend.ps1：调用该接口停止后端，**从此不需要强杀**。

## 6. 重要结论：强杀 vs 优雅停机

真机实测中发现一个**驱动层行为**（不是应用代码能兜住的）：

| 停止方式 | 进程 | COM 口 |
| --- | --- | --- |
| 优雅停机（Ctrl+C / POST /api/shutdown / 关窗） | 立即退出 | **立即释放**（预期，待复测确认） |
| 强杀（Stop-Process -Force / 任务管理器） | HasExited=True，但残留僵尸进程对象 | **可能被 usbser 驱动锁住，直到拔插模块** |

- 强杀会绕过一切清理逻辑，来不及 CloseHandle；
- 一旦驱动把端口锁住，连 pnputil 禁用/启用、remove-device + rescan 都不一定能解开；
- **现场处置：拔插一次 USB-485 模块即可恢复**（本说明中的多次复现都已用拔插恢复）。

因此生产/联调建议：

1. **停止后端一律用 tools/stop-backend.ps1（或 Ctrl+C）**，不要用任务管理器强杀；
2. 若确实强杀过且端口打不开，拔插模块；
3. 服务化部署时用 NSSM 的 CONSOLE 停止方式，它会发送 Ctrl+C，同样走优雅路径。

---

## 7. 仍需注意

1. 旧的卡死进程对象（多个，HasExited=True）会保留在进程表中，设备重新枚举或重启后消失；
   它们锁定的旧 exe 不影响新二进制（新二进制输出到独立目录）。
2. 后续建议：补串口读写单元测试（可用 com0com 虚拟串口对），并按现场调 REOPEN_AFTER_FAILURES 阈值。
