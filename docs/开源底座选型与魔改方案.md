# 开源底座选型与魔改方案（讨论稿）

> 依据 2026-11 的两轮开源调研（平台底座、协议/边缘、级联/消息层），回答「有没有能直接魔改的开源项目」。
> 结论先行：**有，但没有一个项目能原样满足全部需求；推荐以 ThingsPanel 为业务底座魔改，边缘采集与级联服务自研（Rust/Go），消息与存储用宽松许可组件。**

---

## 1. 结论

| 决策项 | 结论 | 理由 |
|---|---|---|
| 业务底座 | **ThingsPanel（Apache-2.0，Go + Vue3）** | 唯一原生「物模型 → 设备模板（含协议配置）→ 协议插件 → 插件生成器」的平台，与「导入模板即接入」的需求同构；代码量小、中文文档全、可白标、已适配人大金仓/TDengine |
| 不采用 | ThingsBoard、JetLinks CE、FastBee、OpenRemote、ThingLinks、DeviceHive | 许可证/规模/维护状态不达标（见 §3） |
| 备选底座 | IoTSharp（.NET 10，Apache-2.0） | 唯一免费内置多租户；但团队需转 .NET，且无公开集群方案 |
| 边缘采集 | 自研 **Rust Agent**（小内存、ARM64 单二进制）+ 复用 NanoMQ/Fledge/Telegraf | 高吞吐、断网续传、私有帧（HJ212/DL645）必须自研；标准 Modbus 可直接用现成件 |
| 消息层 | MQTT：省/区域用 **VerneMQ 或 EMQX 5.8.x（Apache-2.0）**；有预算用 EMQX 6 企业版 | EMQX ≥5.9 改 BSL 1.1，多节点集群需商业授权；TDengine 为 AGPL-3.0，需避开或隔离 |
| 时序库 | **TimescaleDB（自建）或 Apache IoTDB**；TDengine 仅在可接受 AGPL 时使用 | 公有云商用 + 白标交付，AGPL 传染风险高 |
| 级联 | 自研薄「级联服务」+ Broker 单向桥接（Cluster Linking / vmq_bridge） | 调研的 10 个平台无一家有产品化多级级联；这是共性自研项（约 2~3 人月） |
| 接入层 | OpenResty **仅做 L4 与 MQTT over WebSocket**，mTLS 透传 | L4 无法按 topic 限速；TLS 卸载会丢客户端证书 |
| 前端 | 保留 ThingsPanel 的 Vue3 控制台，按本项目品牌与业务改造；监测大屏另做 | 减少重写量 |

**一句话**：不做「从零重写」，做「ThingsPanel 魔改 + Rust 边缘 + 自研级联 + 宽松许可消息/存储」。

## 2. 需求 → 选型映射

| 需求 | 由谁满足 | 缺口/工作量 |
|---|---|---|
| 模板化设备接入（导入模板即接入） | ThingsPanel 物模型/设备模板/协议插件 | 需扩展模板字段（见 §6）与模板市场 |
| RS-485/232/TTL 直连 | Rust Agent / EdgeX 南向 / 串口服务器 | 自研 Agent 约 2 人月 |
| 串口转以太网（raw / RFC2217 / Modbus TCP） | mbusd、ser2net、Agent 内置客户端 | 标准件 + 少量适配 |
| 数采网关 MQTT 上报 | Broker + 级联服务 | 主题规范与鉴权需统一 |
| 多级级联/星型组网 | 自研级联服务 + Broker 桥 | 核心自研项 |
| 省级规模（数千站、数十万点） | 无状态 API + PG + TSDB + Broker 集群 | ThingsPanel 无官方集群，需改造 |
| 多租户/数据权限 | 自研（Apache-2.0 允许） | 6~8 人周；ThingsPanel 企业版才有，但社区版可自行实现 |
| 报警/规则/看板 | ThingsPanel 自动化/告警/可视化 | 够用，按需扩展 |
| 仁科兼容输出 | 自研适配器 | 保留 v1 的迁移/输出能力 |

## 4. 目标架构

```
┌────────────────────────── 省中心（公有云/私有云） ──────────────────────────┐
│  OpenResty(L4/WS) → API 网关 → ThingsPanel 改造版（Go，无状态多副本）        │
│  PostgreSQL(元数据) + TimescaleDB/IoTDB(时序) + Redis                         │
│  Broker 集群（VerneMQ / EMQX 5.8 / EMQX 6 企业版）                            │
│  级联服务（配置下发、命令路由、补传、跨级鉴权、审计）                          │
└───────────────▲───────────────────────────────▲────────────────────────────┘
                │ MQTT/TLS（d/… 上行，c/… 下行）  │ 星型直连（重点站）
┌───────────────┴──────────────┐   ┌────────────┴───────────────┐
│ 区域中心（地市）              │   │ 大型站直连省中心            │
│ Broker + 本地 TSDB + 级联服务 │   │ 同一套主题与鉴权，少一跳     │
└───────────────▲──────────────┘   └────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────────┐
│ 站点边缘（ARM64 工控机/网关）                                  │
│  Rust Agent（采集/模板/缓存/续传/本地告警） + NanoMQ            │
│  或 第三方数采网关（MQTT 直连）                                 │
│  串口：485/232/TTL → mbusd / ser2net / raw TCP / RFC2217        │
└───────────────────────────────────────────────────────────────┘
```

## 5. 级联方案（核心自研）

### 5.1 主题（5 段式，上下行分离）

```
上行  d/{prov}/{region}/{station}/_batch            # 打包遥测，QoS1
      d/{prov}/{region}/{station}/_agg/{period}     # 聚合值
      s/{prov}/{region}/{station}/state             # 在线状态，retain+LWT
      e/{prov}/{region}/{station}/{severity}/{code} # 告警事件
下行  c/{prov}/{region}/{station}/{cmd}             # 命令，带 cmdId
      cfg/{prov}/{region}/{station}                 # 配置版本通告
应答  r/{prov}/{region}/{station}/{cmdId}           # MQTT5 响应主题
```

### 5.2 桥接与防环

- 只桥接明确子树、逐级加前缀，**禁止双向同主题**；
- 优先 Cluster Linking（自动防环），否则 bridge + `noLocal` + 跳数属性；
- 同一对 Broker 只保留一条活跃桥；下行多活用 `$share`。

### 5.3 断网自治与续传

- 站端 SQLite/本地队列保留 7~30 天，断网继续采样与本地告警；
- 恢复后按站限速回放（如 500 msg/s/站），服务端按 `(station,point,ts,seq)` 幂等；
- 服务端做 seq 缺口检测并下发补传请求；消息带 `Message Expiry` 防陈旧数据倒灌；
- 双时间轴：采集时刻 + 接收时刻，容忍乱序。

### 5.4 鉴权

- 设备一机一证 mTLS + 短 TTL JWT（含 region/station claim），ACL 用 claim 变量；
- 级间桥专用账号 + 双向 TLS，只授权必要前缀；
- 命令与数据分离，命令必须经过「命令服务」（审批/限速/审计/回执）。

## 6. 设备模板规范（扩展 ThingsPanel）

模板 = 一个可导入的 JSON 包，至少包含：

| 字段 | 说明 |
|---|---|
| `templateId` / `version` | 唯一标识与语义化版本 |
| `protocol` | `modbus-rtu` / `modbus-tcp` / `modbus-ascii` / `raw-tcp` / `rfc2217` / `mqtt` / `hj212` / `dlt645` / `custom` |
| `transport` | 串口参数（波特率/数据位/校验/停止位）或 TCP（host/port/timeout） |
| `points[]` | `code/name/unit/dataType/register/functionCode/wordOrder/scale/offset/range/deadband/qualityRule` |
| `commands[]` | 写寄存器/继电器/校时等，含回执判定 |
| `sampling` | 默认周期、超时、重试、变化上报阈值 |
| `meta` | 厂商、型号、文档链接、校验和 |

要求：模板可导出/导入、带版本与校验和；平台内置常用模板库；自定义协议通过模板 + 可选插件实现，**不改平台代码**。

## 7. 技术栈与 Rust 的定位

| 层 | 选型 | 说明 |
|---|---|---|
| 控制台/业务 API | Go（ThingsPanel 改造） | 复用现成设备/模板/看板/告警，改造成本最低 |
| 边缘 Agent | **Rust**（tokio + rumqttc + serde + SQLite） | 单二进制、ARM64、低内存、断网续传；满足「高吞吐/可控」诉求 |
| 高吞吐接入旁路 | Rust（可选） | 若 Broker 消费成为瓶颈，用 Rust 写 MQTT→TSDB 批量写入器 |
| 级联服务 | Go 或 Rust | 逻辑不复杂，建议与后端同栈（Go）降低维护成本 |
| 前端 | Vue3 + TS（ThingsPanel 前端改造） | 保留 Arco/TDesign 体系 |
| 反代 | OpenResty（L4 + WS） | mTLS 透传，不在反代终止设备证书 |

> 不建议「中心平台也用 Rust 从零写」：Rust 缺少成熟的 IoT 平台底座，等于放弃 §1 的结论，回到 12~16 个月自研。

## 9. 实施路线（建议 4~6 人）

| 阶段 | 内容 | 周期 |
|---|---|---|
| P0 | 立项/法务确认（ThingsPanel 多租户自研、TDengine 取舍）；搭省中心最小集群 | 3~4 周 |
| P1 | Fork ThingsPanel、白标、模板规范与导入、Modbus 模板打通 | 6~8 周 |
| P2 | Rust Agent（串口/Modbus/raw TCP/RFC2217/缓存/续传）+ NanoMQ | 8~10 周 |
| P3 | 级联服务（主题/桥接/补传/鉴权/命令）+ 区域中心 | 8~10 周 |
| P4 | 多租户/RBAC、TSDB 与查询、报警与报表 | 6~8 周 |
| P5 | 压测（3000 站模拟）、故障注入、信创/ARM64、迁移 | 4~6 周 |

> 关键前置：**先用 2 周做 1000 站模拟压测**（NanoMQ + VerneMQ + TimescaleDB），验证 §5 的主题与桥接设计，再全量开工。
